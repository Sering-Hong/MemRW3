# 构建、测试与 Windows 打包

## 1. 获取源码

```bash
git clone https://github.com/RP27-EC/MemRW3.git
cd MemRW3
```

仓库根目录包含 Cargo.toml；本地已部署目录的仓库根为 `D:\MemRW3\source`。不要在便携程序的上层目录直接执行 Cargo。

## 2. 工具链与系统依赖

使用当前稳定版 Rust 和 Cargo，支持 Rust 2024 edition。项目声明 `rust-version = "1.85"`，但锁定依赖可能要求更新工具链；这里不承诺 1.85 可以构建整个依赖图。本地已验证 Rust 1.99.1、Windows GNU、MSYS2 GCC 15.2。

Windows 可使用 MSVC（安装 Visual Studio C++ 桌面开发工具和 Windows SDK）或 GNU（匹配目标的 MinGW/MSYS2 编译器）。probe-rs、Capstone 等依赖可能需要 C/C++ 编译环境。不要混用不兼容的目标架构和链接器。

Ubuntu/Debian 的基础依赖：

```bash
sudo apt-get update
sudo apt-get install -y build-essential cmake pkg-config libudev-dev libusb-1.0-0-dev libx11-dev libxkbcommon-dev libwayland-dev libssl-dev
```

中文显示可安装 `fonts-noto-cjk`。macOS 的基础工具包括 Xcode Command Line Tools，以及按构建需要安装的 cmake、pkg-config、libusb；本次恢复仅执行 Windows 本地验证。

## 3. 构建和测试

```bash
cargo build --release --locked
cargo test --release --locked
cargo fmt --all -- --check
```

`--locked` 保证使用版本控制中的 Cargo.lock，避免构建时无意升级依赖。首次构建需要下载依赖；仅在已缓存依赖时使用 `--offline`。发布构建输出为 `target/release/MemRW3.exe`（Windows）。

当前恢复采用完整旧源码和已验证的旧程序，避免为了整理文档引入功能变更。源码历史中个别文件存在原有 rustfmt 差异，若格式检查报告差异，先评估再单独提交格式化；不要将格式检查误报成全部通过。实际验证结果见 CHANGELOG。

## 4. Windows 便携包

已安装 Windows Python 3.10+、Rust 和必要 C/C++ 工具链后，在仓库根目录执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\package_windows.ps1
```

脚本构建、测试，复制程序到 `dist\MemRW3`，写入多尺寸粉色图标，并收集 README、CHANGELOG、docs 和快捷方式脚本。还会复制不含 `.git`、target、dist 的仓库源码到包内 `source`。最终生成 `dist\MemRW3-windows.zip`、包内 `SHA256SUMS.txt` 与 ZIP 的 `.sha256` 文件。

如果 Python 未加入 PATH，可用 `-Python "C:\path\to\python.exe"` 显式指定解释器。

如果刚刚完成相同源码的构建和测试，可加 `-SkipBuild`，此时使用现有 `target\release\MemRW3.exe`，并跳过构建及测试。该选项不验证现有二进制是否匹配源码，应由调用者确认。设置 `CARGO_TARGET_DIR` 时脚本会使用该目录中的 release 程序。

脚本只删除并重建本仓库 `dist` 下指定的暂存目录，不会覆盖本地部署的 `D:\MemRW3\MemRW3.exe`。发布时解压生成包，运行程序并验证桌面快捷方式。

## 5. 单独更新 Windows EXE 图标

窗口 PNG 在编译时嵌入；文件图标需要 Windows 原生资源 API：

```powershell
python .\tools\set_windows_icon.py .\target\release\MemRW3.exe .\assets\MemRW3-pink.ico
```

运行该命令前关闭对应 EXE。修改图标会改变程序 SHA256，校验文件应在最后生成。若未来需要代码签名，先修改图标，再签名，最后校验与打包。

## 6. CI 与发布检查

GitHub Actions 针对 main/master 的 push、PR 和手动触发执行 Windows/Ubuntu Release 构建与测试；Windows 额外运行便携打包并上传 ZIP，Linux 上传二进制。首次 push 会排队运行，远端运行结果以 Actions 页面为准，本地通过不等于远端已经通过。

发布前确认：源代码版本、Cargo.lock、文档范围一致；曲线保留起始点；Watch 可展开和搜索；程序图标及快捷方式路径正确；没有误收固件、个人日志、配置或凭据；目标板上的探针、读写、烧录与长时采样已按实际使用场景验证。

## 7. Git 工作流

本仓库保留上游基准提交以及目标仓库的初始 README 提交。新增提交发布到 main，不使用强制推送覆盖历史。`upstream` 指向原项目，`origin` 指向 RP27-EC/MemRW3。

```bash
git status
git diff
git add README.md docs CHANGELOG.md
# 按需加入已经检查的源码和资源文件
git commit -m "docs: update usage guide"
git push origin main
```

不要执行 `git add` 来收集整块 D 盘运行目录。运行目录里的备份包、个人配置、固件、CSV 和构建日志不属于公共仓库。源码构建输出及 dist 包已被忽略。
